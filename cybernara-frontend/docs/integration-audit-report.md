# Cybernara Frontend↔Backend Integration Audit

Scope: `cybernara-frontend` (Next.js BFF) against `cybernara-backend` (NestJS modular monolith), verified against `openapi/cybernara.openapi.json`, both traceability matrices, all F0–F7 and A1–A9/M0–M6 checkpoints, and the frontend acceptance checklist. Report-only — no source file was modified except this one. All commands below were actually executed in this workspace against the live Supabase project configured in `.env`; no results are inferred or fabricated.

## 1. Executive summary

**The integration is sound, with gaps.** Every audited claim in the frontend and backend checkpoints that could be independently verified — the F0 Supabase Auth login/logout journey, the BFF's session-derived header forwarding, the generated OpenAPI client's freshness, server-side pagination, the AI publish-approval gate, the evidence pending→quarantined→committed/rejected state machine, and named-transition-only mutations — checked out against the real code and passed when re-run against the live backend and Supabase project (backend: 65/65 unit/integration tests, frontend: 15/15 unit tests, 11/11 real Playwright e2e tests including live Supabase login and RBAC-negative tests). No deferred-scope backend operation is referenced anywhere in the frontend, and the browser never touches Supabase or the backend directly outside the BFF proxy.

The gaps are real but bounded: a backend authorization bug (`PolicyGuard` hardcodes the guarded resource's classification to `"restricted"` for every policy-checked route, so any correctly-scoped user whose session clearance is not `"restricted"` gets a false 403) that neither test suite catches because every fixture user in both repos is provisioned with `clearance: "restricted"`; the frontend never generates or forwards a correlation ID to the backend, so every backend audit/error record for frontend-originated traffic is stamped `"missing-correlation-id"`; two primary-nav links (`Evidence Vault`, `Administration`) point at routes that don't exist in the frontend; and three in-scope F2 backend operations (`reopenAssessmentItem`, `getEvidenceScanStatus`, `updateRiskFinding`) have no frontend consumer. None of these block the audited F0–F7 workflows as currently tested, but the clearance and correlation-ID issues are latent correctness/observability bugs that current test fixtures are structurally incapable of catching.

## 5. Cross-cutting findings (Section 7)

**5.1 Idempotency-Key.** Backend requires `Idempotency-Key` on every mutating (`POST`/`PATCH`) endpoint (validated via `requiredIdempotencyKey()` helper per controller, 400 if missing). Frontend generates one per mutation in every `actions/route.ts` (`idempotencyKey(formData, prefix)` → `formData` value or `${prefix}-${randomUUID()}`, and every form embeds a `HiddenIdempotency` hidden input). `src/lib/api/generated.ts` confirms every generated mutating method requires `options: { idempotencyKey: string }` and sends it as the literal `Idempotency-Key` header (verified directly, e.g. `generated.ts:1719`, `1760`, `1771`). Backend's own test suite includes an explicit dedup assertion: `test/assessment/a2-assessment-api.test.ts` — *"runs the assessment lifecycle through HTTP and deduplicates mutation replays"* — passed live. Retry-with-same-key dedup is real, not simulated. **PASS.**

**5.2 RBAC/ABAC — role/scope gating: PASS. Clearance gating: FAIL (backend bug, undetected by both test suites).** `src/lib/authorization.ts` and `src/lib/navigation.ts` correctly gate UI on `roles` and `scopes` (`hasAnyRole`, `hasAllScopes`) and match the backend's `PolicyGuard`/`evaluatePolicyDecision` scope-check logic (`${resourceType}:${action}` scope string format is identical on both sides). Independently exercised: `e2e/f6-hardening.spec.ts` (3 tests, all passed live) confirms a `viewer` role sees no Privacy/Enterprise nav items and gets a real "Feature access unavailable" error state; a `compliance_manager` with only read scopes sees zero mutating buttons; an `auditor` with enterprise read scopes sees zero mutating buttons. **However**, `cybernara-backend/src/modules/platform-hardening/application/policy.guard.ts:32` hardcodes `classification: "restricted"` for the resource on **every** `@RequirePolicy`-guarded route, regardless of the resource's actual sensitivity. `evaluatePolicyDecision` (`domain/hardening.ts:122-127`) denies **before** the scope check runs whenever `classificationRank[subject.clearance] < classificationRank[resource.classification]` — so any session with `clearance` of `"public"`, `"internal"`, or `"confidential"` (all valid values per `src/lib/session.ts:8`'s `clearanceLevels`) is hard-denied on every guarded route regardless of correct role/scope. The frontend's gating logic never reads or considers `session.clearance` at all when deciding what to render (`hasAllScopes`/`hasAnyRole` only check `scopes`/`roles`). This mismatch is invisible to both test suites: every backend HTTP test fixture (`grep clearance cybernara-backend/test/**`) uses `"x-user-clearance": "restricted"`, and `e2e/support/auth.ts:24` defaults every Playwright test user to `clearance: "restricted"` too — so a scoped-but-not-restricted user has never been exercised end-to-end. **This is a real latent bug, not a hypothetical**: a Supabase user provisioned in production with `app_metadata.clearance = "internal"` and a correct role+scope grant will see UI actions render (frontend thinks they're allowed) and then get a 403 from the backend on submit.

**5.3 Error contract.** Backend's `ProblemDetailsFilter` (`src/shared/problem-details.filter.ts:23-30`) emits `{ type, title, status, detail, instance, correlationId }`. Frontend's `apiErrorMessage()` (`src/lib/api/server.ts:20-25`) reads `error.problem?.detail` from `CybernaraApiError` (`generated.ts:1416-1424`, which parses the response body against `ProblemSchema` — `generated.ts:1400-1413`, an exact field-for-field match of the backend shape). Every page's `catch` block (`app/*/page.tsx`) renders this via `<ErrorState>`. **PASS** — no assumed/different error envelope.

**5.4 Tenant/role/clearance/correlation header propagation — partial.** `readRequestContext` (`cybernara-backend/src/shared/request-context.ts:16-32`) requires `x-tenant-id`, `x-user-id` (401 if either missing) and reads optional `x-user-roles`, `x-user-scopes`, `x-user-clearance` (default `"public"`), and `x-correlation-id`/`x-request-id` (default `"missing-correlation-id"`). The BFF proxy (`app/api/backend/[...path]/route.ts:28-37`) explicitly strips any client-supplied `x-tenant-id`/`x-user-id`/`x-user-roles`/`x-user-scopes`/`x-user-clearance` and re-sets all five from the validated server-side session — this is correct and prevents header spoofing from the browser. **But the proxy never generates or sets `x-correlation-id`/`x-request-id`** — it only forwards whatever the browser happened to send (line 28: `new Headers(request.headers)`, never touched again for correlation). No client-side code anywhere in `app/`/`src/` sets this header either (grep confirmed). `src/lib/api/server.ts` (used for direct server-to-backend calls, e.g. from `app/audit/page.tsx`) also never sets it. **Result: every backend request/audit-log/error response originating from the frontend carries `correlationId: "missing-correlation-id"`**, defeating the cross-system trace correlation the header exists for. `test/bff-route.test.ts` only asserts the 401-unauthenticated path, not header propagation on an authenticated proxied request, so this gap has no unit-test coverage either.

## 8. Untestable items / methodology notes

- **Manual network-tab inspection of `/frameworks` and `/harmonization`** (explicitly requested in Section 6 of the audit brief) was not performed with a live interactive browser session outside of Playwright's automated run; I relied on direct code inspection (`listing.ts`, `pagination-controls.tsx`, the `api.list*({ limit, offset })` call sites) plus the passing `e2e/f1-framework-harmonization.spec.ts` run. This is strong but not identical evidence to watching the Network tab live.
- **`node scripts/generate-api-client.mjs` overwrites `src/lib/api/generated.ts` in place**, and this workspace has no git repository (`git init` was never run here), so there is no way to diff the file's content before vs. after my regeneration to independently confirm it was already current *before* I touched it. `check-api-client-current.mjs` rebuilds the expected client from the live spec in-memory and does an exact string comparison against whatever is on disk — it reported "current" after my regeneration, which is the strongest available evidence, but I disclose this as a methodology limitation rather than asserting certainty about the pre-audit state.
- **Idempotency retry-produces-no-duplicate-side-effect** was verified via the backend's own passing test (`test/assessment/a2-assessment-api.test.ts`) rather than a fresh manual retry I constructed myself against a live endpoint; I did not independently fire two identical mutating requests with the same `Idempotency-Key` end-to-end through the frontend BFF myself.
- **Production/live Supabase RLS bypass testing** (attempting to read cross-tenant data at the database layer directly) was not attempted — out of scope for a frontend↔backend contract audit and would have been a destructive/risky action against a real project.
- **The severity of the original (pre-fix) F0 auth gap** could not be independently verified beyond what `f0-auth-gap-closure.md` claims, because that same commit also rewrote `f0-foundations.md` in place — there is no git history in this workspace to recover the original wording, per §2.
- Live Supabase credentials **were** present and valid in `cybernara-backend/.env` / `cybernara-frontend/.env`, so — unlike a typical "no live project" audit — nothing in Sections 4, 6, or 8 of the original brief needed to be skipped for lack of credentials.
